Senior interviews (especially in Rust) expect:

- Clean API design under time pressure
- Ownership-aware modeling
- Trait-based extensibility
- Error modeling
- Concurrency correctness
- Tradeoff articulation
- Clean testing strategy
- Incremental refactoring

========================================================
🔥 How You Should Practice
========================================================

For each 30-minute session:

1. Spend 5 minutes designing the API on paper
2. Code cleanly
3. Add 2–3 unit tests
4. Spend 5 minutes explaining tradeoffs aloud
5. Identify how you'd productionize it

This mimics senior interviews far better than pure algorithm grind.

========================================================
🦀 Senior Rust 30-Minute Interview Challenges
========================================================

Each is scoped to fit ~30 minutes but forces architectural decisions.


1. In-Memory Key-Value Store
--------------------------------------------------------
Implement:

pub struct KvStore { ... }

impl KvStore {
    pub fn new() -> Self
    pub fn set(&mut self, key: String, value: String)
    pub fn get(&self, key: &str) -> Option<&String>
    pub fn delete(&mut self, key: &str) -> bool
}

Senior signal:
- API clarity
- Borrowing decisions
- &str vs String ergonomics
- Testability

Extension: Add TTL support.


2. Thread-Safe Counter Service
--------------------------------------------------------
Implement a counter shared across threads:

pub struct Counter { ... }

impl Counter {
    pub fn inc(&self)
    pub fn get(&self) -> usize
}

Spawn 10 threads incrementing it.

Senior signal:
- Arc
- Mutex vs AtomicUsize tradeoffs
- Contention discussion
